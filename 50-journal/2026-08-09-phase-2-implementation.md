## Key design decisions

### Contract and data model

1. **Deterministic `tool_id`**: Enables idempotent tool resolution and ensures that the same tool version from the same framework plugin produces the same identifier.

2. **Side-effect classification**: Tools are classified by side-effect class (`read_only`, `write`, `network`, `stateful`) to enable capability policy enforcement and resource bounding.

3. **Capability binding**: Each tool is bound to a capability identifier that determines the minimum privilege required to use it.

4. **Framework plugin origin**: Tools originate from framework plugins, which are isolated in their own tenant and subject to the framework plugin manifest contract.

5. **Tenant scope enforcement**: The `tenant_scope` field ensures that retrieval operations are scoped to the appropriate tenant boundaries.

6. **Content deduplication**: The `content_ref` field enables deduplication of retrieval results and prevents redundant storage of identical content.

7. **Citation and provenance**: Each retrieval item includes a citation string for attribution and provenance.

8. **Immutable execution environment**: The `environment` field specifies an immutable execution environment (e.g., Docker image) to ensure reproducibility and security.

9. **Resource budgeting**: The `resource_budget` field enables per-request resource bounding to prevent resource exhaustion.

10. **Isolation classes**: The `isolation_class` field enables different levels of isolation based on the trust level of the code (`shared`, `tenant`, `isolated`).

11. **Redacted storage**: The `code`, `stdout`, and `stderr` fields are stored with redacted references to protect sensitive data.

12. **Artifact tracking**: The `artifacts` field tracks output artifacts (e.g., files, images, data) generated by code execution.

### Behavior and integration

1. **Framework plugin querying**: Tools originate from framework plugins, which are approved by the host and isolated in their own tenant.

2. **Descriptor validation**: Invalid tool descriptors are excluded from the catalog to prevent agents from using tools with malformed schemas.

3. **Status filtering**: Tools with status `deprecated` or `suspended` are excluded from the catalog.

4. **Capability-based filtering**: The catalog is filtered based on the agent's capabilities to ensure that agents only see tools they have been granted access to.

5. **Tenant scope enforcement**: Tenant scope filters ensure that tools do not expose cross-tenant data.

6. **Durable effect attempts**: Tool executions are mediated through durable effect attempts to ensure auditability, replayability, and crash-resistance.

7. **Capability pre-check**: The host checks capabilities before creating the effect attempt to avoid wasting resources on unauthorized executions.

8. **Catalog validation**: The host validates that the tool is active and available in the filtered catalog before executing.

9. **Bounded execution**: The execution is bounded by the `timeout_ms` and `resource_budget` fields to prevent resource exhaustion.

10. **Result normalization**: The host normalizes tool results into a common format to ensure consistency across different tool implementations.

11. **Result signal emission**: The host emits a `tool.execution.result` signal with the normalized result to enable downstream components to react to tool execution results.

12. **Atomic rejection**: Every failure outcome MUST reject without creating partial execution or result state.

13. **Schema validation**: Schema validation is performed both for inputs (before execution) and outputs (after execution) to ensure data integrity.

14. **Safety filtering**: Unsafe outputs are rejected to prevent the propagation of harmful content.

15. **Partial results**: Partial connector results are accepted but marked as partial in diagnostics to enable downstream components to handle incomplete data appropriately.

16. **Provenance requirements**: Tools that require provenance evidence must capture it during execution. Missing provenance results in rejection to ensure auditability.

### Failure evidence

1. **Atomic rejection**: Every failure outcome MUST reject without creating partial execution or result state.

2. **Consistent diagnostic format**: All diagnostics follow a consistent naming convention (`tool.request.*`, `tool.execution.*`, `tool.result.*`).

3. **Cross-tenant rejection**: Cross-tenant data access is rejected outright to prevent authority leaks.

4. **Safety and provenance**: Safety-related and provenance-related diagnostics emit warnings in diagnostics to enable downstream filtering and auditing.

5. **Bounded diagnostics**: Diagnostics identify the phase contract, profile, and failed boundary without exposing secrets.

6. **Tamper-evident evidence**: The `evidence_digest` field enables downstream systems to verify that the evidence record has not been tampered with after creation.

7. **Comprehensive evidence types**: The evidence types cover all phases of tool/retrieval/code execution: requested, completed, failed, cancelled, and result.

8. **Contextual fields**: The `tool_id` and `language` fields provide additional context for tool and code executions, respectively.

9. **Documented constraints**: Implementation-defined choices are documented in the conformance profile to ensure they are auditable and transparent.

10. **Deferred work**: The deferred work items are not within the scope of Phase 2 but may be addressed in future phases.

### Integration tests

1. **Observable behavior**: Tests verify observable behavior (signals, durable journal entries) rather than private implementation structure.

2. **Capability visibility**: Tests verify that tools are visible only to agents with the required capability.

3. **Idempotent execution**: Tests verify that idempotent tools produce the same result on retry.

4. **Resource tracking**: Tests verify that resource usage is recorded.

5. **Provenance capture**: Tests verify that provenance evidence is captured for tools that require it.

6. **Tenant scope**: Tests verify that tenant scope filters are enforced.

7. **Content deduplication**: Tests verify that content references are included for deduplication.

8. **Sandbox enforcement**: Tests verify that sandbox restrictions are enforced.

9. **State invariants**: Each failure test verifies that the host does NOT create partial execution or result state.

10. **Stable diagnostics**: Each failure test verifies that the expected diagnostic is emitted.

11. **Comprehensive failure coverage**: The tests cover all failure outcome categories: malformed, incompatible, conflicting, unauthorized, exhausted, unavailable.

12. **Timeout scenarios**: The tests cover both the implementation-defined timeout and the agent-specified custom timeout for tool, retrieval, and code execution.

13. **Cancellation timing**: The tests verify cancellation behavior at different points in the lifecycle (during execution, after completion).

14. **Concurrent cancellation**: Tests verify that concurrent cancellation requests are handled correctly (only one is processed).

15. **No partial state**: All timeout and cancellation tests verify that no partial state is left in the durable journal.

16. **Comprehensive scope**: The tests cover 12 fixture scopes from 6 milestones to ensure Phase 2 does not introduce regressions.

17. **Indirect effects**: The scope accounts for indirect effects through shared subsystems (such as the agent registry, mailboxes, and durable journal).

18. **Baseline comparison**: Each fixture is compared against a baseline to detect regressions. Any deviations are documented as approved variability.

19. **Revision protocol**: If any fixture fails, the Phase 2 implementation MUST be revised and the affected milestone MUST be re-validated.

20. **Tamper-evident evidence**: The `evidence_digest` field enables downstream systems to verify that the evidence record has not been tampered with after creation.

21. **Signed evidence**: All evidence records are signed according to the provenance and audit mechanism.

22. **Reproducible**: The evidence format enables reproducible test runs that can be verified independently.

23. **Narrative context**: The written report provides context and narrative that structured evidence records cannot capture.

## Open questions

1. Should tools be versioned independently or as part of the framework plugin?

2. Should the `tenant_scope` field support hierarchical scoping (e.g., `organization.team.agent`)?

3. Should code execution support stateful sessions or only stateless executions?

4. Should connector authentication be handled by the host or by the agent?

5. Should the host cache the filtered catalog or regenerate it on each request?

6. Should tool execution support streaming results or only final results?

7. Should the host retry on `tool.execution.sandbox_failure` or reject outright?

8. Should provenance loss be a hard rejection or a warning?

9. Should the test evidence include the full input/output data or just a hash?

10. Should cross-milestone tests run automatically or manually?

11. Should implementation-defined choices have default values or be required?

12. Should sandbox network access be disabled by default or enabled by default?
